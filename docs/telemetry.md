# Engineering event ingestion (draft)

EventStore persists only normalized allowlisted metadata for agent, CI, GitHub and Linear sources. It deduplicates provider event IDs, rejects conflicting duplicates, retains out-of-order events and exposes a bounded durable outbox. Unknown cost/usage stays explicitly unknown, not zero. Stable trace/span identifiers are derived from verified repository/issue mapping and provider event identity.

The SDK adapter emits normalized events as OpenTelemetry spans through a tested OTLP transport; Grafana export remains unconfigured. Authenticated GitHub/Linear intake, explicit issue resolution, atomic durable export claims and a bounded operator worker are implemented, with local fixtures and read-only GitHub source snapshots as evidence. The complete local suite passes 43 tests. Four live authenticated source deliveries remain unverified. No raw webhook, prompt, review body, source code, email or credential may be stored. Do not pass a raw provider payload as attributes. Repository/issue correlation is approved resource metadata, not permission to collect personal attributes.

Use SQLite on a persistent encrypted volume with restricted permissions and approved retention. The outbox is at-least-once: a crash after external export and before acknowledgement can re-export an event. Deterministic IDs help correlation but do not guarantee backend deduplication. Do not derive current issue/PR state merely from arrival order; a future projection must handle source revisions/reconciliation explicitly. Database/file size, pruning and operational recovery remain incomplete.

Grafana credentials/scope and production endpoints remain blocked on owner KEB-129 setup. No data has been exported to Grafana and no Grafana resources created. KEB-130 acceptance requires actual source samples and end-to-end export, not local fixture tests.

## Linear signed issue adapter

`receive_issue` verifies HMAC-SHA256 over the original bounded raw bytes using constant-time comparison, then requires the signed webhookTimestamp to be within 60 seconds of a trusted receiver clock. Organization, issue UUID-to-repository/identifier mapping and state UUID mapping are explicit trusted configuration. Only Issue create/update events are accepted; unknown scope/state fails closed. Actor, title, description and other payload content are discarded. A logical event key uses signed issue/update/state/action metadata so repeated delivery does not create more state events.

Three additional tests cover signed normalization/deduplication, wrong signatures, replay/future timestamps, organization/issue scope, unknown state and boolean timestamp rejection. Production HTTPS endpoint, secret provisioning, real signed Linear delivery and four-source live correlation remain unverified. Linear requires HTTP200 for successful delivery and retries non-200 failures; the HTTP adapter preserves that contract for accepted deliveries and durable duplicates. See https://linear.app/developers/webhooks .

## Authenticated GitHub telemetry intake

`telemetry.github.receive` validates HMAC over the bounded raw body before parsing or resolving issue mappings, then enforces repository-to-installation allowlisting. It accepts only workflow_run/PR events and requires a trusted resolver to establish the issue relationship. PR deduplication uses signed lifecycle metadata rather than an unsigned delivery header or a digest of private body text. No raw payload is persisted. Three additional tests verify signature-before-resolver ordering, installation scope, missing mappings and replay/privacy behavior; all 16 tests pass locally.

The resolver must use verified project/PR/commit relationships, not blindly trust issue-looking strings in titles or body text. GitHub has no signed global delivery timestamp here; durable logical deduplication handles exact lifecycle replays, while reconciliation and bounded storage/retention remain operational requirements. Live signed GitHub delivery and deployed HTTP routing are not established by these synthetic tests.

A PR event can resolve through either verified relationship; a workflow with no PR uses its exact commit mapping. Conflicting PR/commit associations, workflows listing multiple PRs, unknown relationships and malformed identities remain unresolved and are rejected by the authenticated receiver. Titles, descriptions and branch names never supply attribution. The resolver snapshots configuration; obtaining and refreshing reviewed mappings from GitHub/Linear remains an operational requirement. ## Webhook HTTP adapter

telemetry.http.application accepts an explicit path-to-receiver mapping. Bind separate GitHub and Linear routes to the authenticated receivers above; callbacks must complete durable storage before returning and obtain a per-request database connection. It returns HTTP200 for valid deliveries including duplicates, HTTP400 for invalid signatures/payloads and HTTP503 for storage/I/O failures without exposing exception details. Unknown routes, methods, content types, missing/invalid lengths, oversized bodies and truncated reads are rejected before invoking receivers. Requests are limited to 1MiB.

A production WSGI server and TLS proxy must enforce request/read timeouts, connection limits, header limits and body limits before dispatch; this adapter does not provide those controls. No server is deployed. Three adapter tests exercise transport rejection, signed Linear delivery and replay into the real event store, and retryable database failure. ## OTLP protobuf export

telemetry.otlp.OtlpExporter implements the SDK SpanExporter interface using the pinned OpenTelemetry protobuf encoder and requests transport. Supply the complete traces endpoint ending in /v1/traces, its exact trusted hostname and the ingestion authorization header from a secret store. The Grafana dashboard URL is not an ingestion endpoint. Call export_pending(store, exporter) and always close the exporter with shutdown() afterward. Do not log the authorization header or put it in a URL, source file or command argument.

Production endpoints require HTTPS with certificate verification and port443. Environment proxy/netrc settings are disabled; redirects are never followed. Requests are capped at1MiB and response acknowledgements at64KiB, with connect/read timeouts of3/5seconds. These are socket timeouts, not a total wall-clock deadline; the worker supervisor must impose an overall deadline. Only HTTP200 with a valid protobuf response and no partial rejection/warning acknowledges the durable outbox. Non-success, malformed replies and partial rejection retain the event for a later bounded retry; this exporter performs one request per attempt and never logs response bodies. A crash after remote acceptance but before local acknowledgement can still duplicate delivery.

An explicit local_fixture option permits only unauthenticated HTTP to127.0.0.1 for controlled tests. Three tests use a real loopback HTTP server to decode emitted protobuf spans, verify acknowledgement, reject redirects/errors/partial responses and validate destination/credential inputs. All23 local tests pass. This proves local protocol transport, not Grafana ingestion, TLS deployment, live four-source correlation or dashboard metric production. Protocol references: https://opentelemetry.io/docs/specs/otel/protocol/exporter/ and https://opentelemetry.io/docs/languages/python/exporters/ .

## Initial Prometheus projection

telemetry.metrics.render_metrics reads the complete durable event history for an explicit repository allowlist. It emits agentic_ci_attempts_total (attempt=1 or retry, outcome=success or failure), agentic_tokens_total (type=input or output) and agentic_metric_source_events_total (source). CI identities are repository/run ID/attempt, so repeated metadata does not double-count; conflicting terminal outcomes fail the whole projection. Skipped, neutral, cancelled and unknown outcomes are excluded from the CI denominator. Tokens sum reported per-turn usage independently; missing usage emits no sample, and totals may be partial. No price inference or actual-cost metric is emitted. Source-event counts describe observed records, not delivery completeness.

Only repository, finite source/outcome/attempt/type labels are exposed; issue IDs, run IDs and event IDs stay out of metric labels. The projection includes already-exported events so span acknowledgement cannot reset counters. It requires append-only retained history: do not prune records or restore an older database while serving the same cumulative series without an explicit counter-reset/reconciliation plan. Late historical events increment counters when received, not retroactively at their source timestamp. This limits historical rate/lead-time interpretation. Default limit100000 selected records (maximum configurable1000000) fails closed rather than truncating totals; a larger deployment needs a durable incremental projection before exceeding that bound.

telemetry.metrics_http.create_metrics_application serves GET /metrics with a separate explicit bearer credential (at least32 characters), constant-time comparison, no-store responses and Prometheus text0.0.4 Content-Type. Configure a read-only SQLite connection factory against the existing event database and the approved repository scope; unauthorized requests never open the database. Projection/storage failures return generic HTTP503, not zero totals. Host behind the production TLS proxy with header/read/connection limits; do not expose plaintext credentials or enable public scraping. No scraper, remote-write destination or Grafana resources are configured here.

Four seeded integration tests verify cross-repository filtering, first attempts/retries/skips, replay and terminal-conflict behavior, reported/missing tokens, export-ack stability and authenticated read-only scraping. All30 local tests pass. Remaining producers include run-level lifecycle, substantive reviews, issue-to-merge history, actual billing/cost coverage, intervention, confirmed defects, pending remediation, deployment outcomes and source lag. Dashboard rendering, per-issue/model drill-down and alerts remain incomplete. Text protocol reference: https://prometheus.io/docs/instrumenting/exposition_formats/ .

## Durable exporter claims

export_pending atomically claims one event at a time under a unique worker ID using SQLite BEGIN IMMEDIATE. Claims persist across connections/restarts and expire after300seconds. Only the same unexpired worker may acknowledge its event; an expired worker cannot acknowledge or release a replacement claim. Known exporter failure releases the claim for a later retry. A crash leaves the claim until expiry. A slow/stopped worker may still have sent data when its lease expires, so this does not provide exactly-once remote delivery; enforce an external worker deadline shorter than the lease and maintain a trusted receiver clock. pending() remains a diagnostic read, not a worker reservation. Do not use the low-level acknowledge() helper in concurrent exporters.

Four two-connection/recreation tests cover exclusion, expiry fencing, release/retry and bounded lease validation. All35 tests pass, including the combined HTTP/OTLP fixture using claimed export. Operational worker supervision, clock monitoring and backend deduplication/reconciliation remain required.

## Operator export worker

Run the reviewed platform artifact with python -m telemetry.worker after installing telemetry/requirements.txt in its isolated runtime. Supply AGENTIC_TELEMETRY_DB, AGENTIC_OTLP_TRACES_ENDPOINT, AGENTIC_OTLP_HOST and AGENTIC_OTLP_AUTHORIZATION through trusted runtime configuration/secret references, never command arguments or repository-controlled processes. The database must already contain the ingestion schema, be a regular file owned by the worker user with no group/world permissions, and live in an operator-controlled directory on the approved encrypted volume. Use a restrictive umask when ingestion creates it. Symlink files, absent schema and accidentally public databases are rejected. Parent-directory integrity and encrypted storage remain operator responsibilities.

Each invocation exports at most100 events with durable claims and always closes its database/exporter. Standard output contains only delivered/pending counts, or a generic unavailable status on configuration/storage failure. Exit75 requests a later bounded retry for failure, leased pending work or a partial batch; a complete100-event batch may still leave pending work and returns0. The scheduler must continue periodic batches while pending is nonzero, enforce a process deadline shorter than the300-second claim lease, cap retries/backoff and surface backlog/health to operators. No scheduler/deployment is configured here, and Python/socket timeouts alone are not a hard process deadline.

Four worker tests cover persistent acknowledgement/recreation, resource closure, protected database checks, generic failure output and partial-batch retry exit behavior. All39 local tests pass. No credentials or external endpoint were used in these worker fixtures.

For supervised execution, activate the reviewed isolated Python runtime and invoke scripts/run_telemetry_export.sh. It runs the worker through the platform timeout utility with a default120-second deadline, TERM then KILL after5seconds, including the worker process group. AGENTIC_EXPORT_TIMEOUT_SECONDS may be an integer1–240; invalid values or extra arguments fail before starting the worker. Even the maximum245-second deadline/grace stays below the300-second event lease. The wrapper changes to its trusted artifact directory and accepts no command override. timeout and bash must be installed; the activated runtime must supply python3 and pinned telemetry dependencies. A scheduler must classify timeout124/forced-kill status as an unknown export outcome, retain claims until expiry and retry/reconcile later, without assuming the remote receiver rejected the event.

Four actual-process tests verify worker exit preservation, rejection of invalid/injected/overflow deadline strings, termination of worker/descendant and forced termination when TERM is ignored. All43 local tests pass. This proves the local wrapper process boundary, not an installed production scheduler, immutable runtime permissions, live endpoint or encrypted persistent host.

## Confirmed review submissions and unknown classification

Signed `pull_request_review` submitted events now use the same signature, repository/installation and explicit PR/commit issue mapping checks as other GitHub deliveries. Store only PR/review IDs, reviewed commit SHA, submission timestamp, finite review state and evidence classification. Review bodies, inline text and reviewer identities never persist or become span/metric attributes. Edited/dismissed events are not new submissions; historical reviews may target an older commit and are not incorrectly discarded as stale remediation work.

Approved and changes-requested submissions count as explicit decisions. A commented submission counts only when `InlineReviewEvidence` verifies a positive, linked comment ID and path from the authenticated review-comments endpoint. It requests only the first comment; it is testing existence rather than counting findings. The API may expose legacy position fields or file-level comments instead of line fields; neither is needed to establish a linked review comment. Inject a trusted read-only, fixed api.github.com transport with bounded responses/timeouts and no redirects, using approved App installation credentials. Never use webhook body text or agent-supplied JSON as evidence. The WSGI factory accepts an optional evidence adapter; without one, commented reviews remain unclassified. Transport/malformed-evidence failures do not ingest a guessed classification.

`agentic_review_cycles_total{repository}` counts observed confirmed submissions, not review comments or attempts to request a review. `agentic_review_unclassified_total{repository}` counts observed submissions lacking enough evidence, including comment-only summaries and rate-limit notices. Issue comments and review-request chat commands are not subscribed review submissions. A body-only real review may remain unclassified; the dashboard must label confirmed cycles partial until provider-specific classification and delivery reconciliation are accepted. If only unclassified reviews exist, no zero confirmed-cycle sample is fabricated. The separate unknown counter does not prove global delivery completeness.

The stable identity is repository/PR/review ID, independent of delivery ID. A replay reuses persisted classification without another API fetch; changed immutable review metadata fails closed. A later API response or configuration change does not silently reclassify history. Correcting an unclassified historical review requires explicit reconciliation, not deleting events or resetting cumulative counters. Logical duplicate imports do not inflate metrics; conflicting review identity/state/commit/timestamp/issue/classification fails the projection. Labels remain repository-only, not reviewer/review/PR IDs. Outbox acknowledgement does not remove review history.

Eight new tests cover decisions, legacy inline evidence, body-only/rate notices, missing adapter, signature/installation/mapping rejection, replay without API calls, malformed evidence, ignored actions, logical duplicates/conflicts and repository isolation. The existing four-source HTTP/protobuf integration now carries six events, including two signed review submissions with duplicate deliveries, and verifies retained confirmed/unclassified totals after export. The full local suite passed51 tests; changed review and actual loopback/protobuf tests were rechecked after the live API adjustment. This is metadata-adapter evidence, not approved App transport, signed live delivery, Cloud export or production review completeness. No GitHub comment, review or remote configuration was changed.
