# Observed issue-to-merge lead time

The producer joins authenticated, explicitly mapped Linear issues and GitHub PRs. Linear's entity `data.createdAt` supplies `issue_created_ns`; the top-level webhook action timestamp does not. GitHub's `pull_request.merged_at` supplies `merged_ns`; neither delivery time nor `updated_at` substitutes for it. Both metadata fields must be bounded integers with the correct source/kind and must not exceed the event's source timestamp. Missing fields in older records remain unknown.

Each repository/issue contributes one duration from creation to its earliest associated merge observed before completion is counted. PR identity is unique within a repository. Repeated deliveries and multiple later PRs cannot inflate the histogram; a PR mapped to different issues, conflicting creation times or conflicting merge times require reconciliation. Issue/PR identifiers remain event metadata, never Prometheus labels. Repository labels use the existing explicit scrape allowlist.

The cumulative histogram uses 60, 300, 600, 1800, 3600, 14400, 86400, 604800 and 2592000 second buckets plus `+Inf`, count and sum. A verified creation provides a zero baseline before observed merges. A repository with no creation evidence has no histogram samples. Zero completed observations produces an Unknown quantile rather than a fabricated duration. The `agentic_issue_to_merge_incomplete` gauge counts distinct observed merged issues excluded for missing creation, missing merge time, invalid timing or legacy receipt metadata. These are observed exclusions, not evidence of complete provider delivery.

Projection replays immutable receiver sequence order, not source timestamps or lexical event IDs. A merge may arrive before its issue creation and still join correctly. Once an issue has contributed a sample, a later earlier merge, unresolved merge timing or changed creation/relationship metadata must not rewrite cumulative bucket history. Those cases fail the metrics projection and the protected endpoint returns its generic unavailable response. Durable events remain intact. A trusted operator must reconcile the full associated history, then establish a new metric baseline; this change provides no automatic history edits, receipt backfill, deletion, counter reset or recovery command. Plan the Prometheus baseline/window handling before resuming collection. Retain both event and receipt history; export acknowledgement never removes either.

Selected dashboard ranges apply to increases between scrape observations. Late creation/merge deliveries can add a historical completion to a later scrape window. The panel is explicitly partial: it does not claim source-event-time windowing, complete PR discovery, synchronized provider clocks or a fully reconciled historical cohort. Full acceptance still needs approved live mappings, delivery reconciliation and Cloud collection.

The disposable integration fixture sends real signed Linear/GitHub requests through the WSGI adapters, stores the records/receipts and scrapes the actual projection. It seeds 240 completed issues per repository during the first 20 minutes, followed by 40 quiet minutes. Alpha's bucketed p50 is 300 seconds, beta's 600 seconds and their combined p50 450 seconds. Exact raw count/sum/buckets and excluded-observation gauges are checked before Prometheus/Grafana validation. No live issue, PR, model call, account or credential is used.

Source schemas: [Linear webhook payloads](https://linear.app/developers/webhooks) and [GitHub pull-request webhooks](https://docs.github.com/en/webhooks/webhook-events-and-payloads#pull_request).
