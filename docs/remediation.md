# Bounded review remediation

This is the durable intake and dry-run scheduler for KEB-128. It is not a deployed webhook service or an enabled coding worker. There is no GitHub write client, agent runner, approval API or merge API in this package. CodeRabbit review text is untrusted data, never a command. No source files, comment bodies, prompts, tokens or webhook secrets are stored in its database or exported job requests.

## Current interface

`Intake.receive(event, signature, raw_body)` checks an HMAC-SHA256 signature with constant-time comparison before parsing JSON or fetching GitHub data. Supply a secret of at least 32 bytes from secret storage, explicit repository-to-installation IDs and the API-verified CodeRabbit bot user ID. A deployment adapter must preserve the exact raw request bytes and reject requests over 1 MiB before buffering. It must translate malformed JSON/fields/signatures to generic HTTP errors without logging request contents. Unsupported events/actions are ignored.

The injected `ReviewSource.current_review` must fetch the PR, comment and its current thread through the authenticated GitHub API. It must verify the comment belongs to that PR, resolve author identity by numeric ID, and determine resolved/outdated status from thread metadata. Missing or ambiguous metadata must fail closed. The webhook's embedded body/head/author are not trusted as current evidence. API errors must not acknowledge successful processing: retry delivery after bounded backoff and respect GitHub rate limits.

Only open same-repository feature PRs with an unresolved, current-head CodeRabbit comment can queue. Main/master are denied; the future adapter must also deny every protected/default branch discovered from repository policy. Sensitive paths and suspicious review text go to needs-human. This classifier is conservative routing, not a proof against prompt injection. Raw review text never reaches the scheduler's output. A coding worker will need independent verification of the reported bug from source before deciding whether to act.

SQLite stores a unique repository/PR/head/comment key. Edited comments for an existing key do not create more work; the scheduler refetches current review/head/thread metadata before claiming. Changes invalidate the candidate. Duplicate delivery and process restart do not reset the queue or attempt count. Keep this database on a persistent encrypted volume, restrict file permissions to the service user, back it up and define a retention policy before hosting. It is not suitable on ephemeral function storage. One transaction and a unique partial index enforce one running attempt per PR across database connections.

`claim_dry_run` returns a reference-only request with a maximum 300-second deadline, dry-run mode and zero spend limit. At most three total attempts are reserved per PR across comments and head changes; this is stricter than three retries. A failed/expired attempt requires human review. Expired running leases remain locked until a human verifies that the old worker has stopped; they are never automatically reused. A worker supervisor must enforce process termination at the deadline: the database deadline alone cannot terminate a process. `finish_dry_run` records completion and rejects duplicate completion. These scheduler records are not owner approvals.

## Worker and publishing design

Before adding a live adapter, Mason must approve the GitHub App identity, repository selection, endpoint and spend ceiling. Proposed permissions: metadata read, pull requests read, contents write only where branch patch publication is approved, and narrowly scoped issue comments for explanations. Do not grant administration, workflows write, bypass rights or pull-request review/merge authority. Confirm the current GitHub endpoint permission requirements when implementing the adapter; do not silently increase permissions. Required PR checks and branch protection must stay enforced.

The intake host authenticates a webhook, commits durable work, then responds quickly. A separate worker claims a job and fetches the exact head into an ephemeral isolated workspace. It has no personal Mac credentials, webhook secret, GitHub App private key or cloud credentials. Its network access must be limited to the approved model gateway, dependencies and source-fetch mechanism; it cannot run untrusted PR code on a personal self-hosted runner. It receives finding references, verifies the bug and produces an artifact containing a patch, changed-file manifest, explanation and check results. Disagreements and security-sensitive changes go to Mason.

A trusted supervisor enforces the wall-time ceiling and atomically reserves the approved worst-case cost before starting an agent. Unknown prices or missing budgets must block a paid run; actual cost must not be guessed. The owner-approved monthly ceiling is separate from the £5–£10 AWS development target. Retries and a changed head cannot reset the spend ledger. A crash retains reservations until reconciled. The initial implementation intentionally has no paid execution path.

A separate minimal publisher validates the patch against the original head and permitted paths, rejects workflow/auth/infrastructure changes, independently reruns required checks in the isolated environment and rechecks the live head. It may update only the same approved PR branch using compare-and-swap; a moved head causes needs-human, never a force push. An installation-token push should trigger hosted checks. Publishing an explanation must use a reviewed sanitized template and must not quote untrusted review instructions. The service must not submit approvals, resolve disagreements by itself or merge. Installation permissions and protected-branch rules provide additional enforcement beyond the absence of those API methods.

## Read-only GitHub adapter

`GitHubReviewSource` implements current PR/comment/thread lookup using `GitHubJSON` and an injected temporary-token provider. The transport uses fixed api.github.com endpoints, refuses redirects, caps responses at 2 MiB and times out each request after ten seconds. It binds comment ID/PR URL, supports only root findings, checks protected/default branches and drafts, and scans at most ten pages of 100 thread roots. Missing threads, replies, incomplete metadata, query errors and invalid pagination fail closed. This bounded lookup intentionally escalates unusually large PRs instead of guessing. The publisher must still recheck the live head immediately before any future branch update.

Six additional adapter tests use fake API responses. A read-only live query verified the thread fields against GitHub; a live approved App installation and full transport integration are still unverified. Do not infer deployed authentication from that schema probe.

## Durable budget ledger

`Budget` reserves integer micro-USD worst-case costs atomically against a separately owner-approved UTC monthly ceiling. Missing limits/prices block reservation. A run identity cannot be reserved twice; retries use new identities against the same shared ceiling. Unknown outcomes retain their reservations across crashes/restarts. Known actual cost is reconciled once; conflicting settlements fail, while overruns are recorded and block further spending. There is no automatic release of abandoned work.

This ledger does not itself stop API billing. The execution handoff below now supplies the UTC period and connects attempt leases to reservations and cost reconciliation, but the coding worker/model gateway must still enforce model/token/runtime limits and stop work at month boundaries. Repository/webhook input must never choose the ceiling, period, price or settlement. Cross-provider currency conversion and billing lag still need explicit handling before enabling paid execution. Six budget tests exercise shared limits, restart retention, unknown prices, settlement, overruns and retries.

## Publication validation primitives

`validate_manifest` accepts at most twenty ordinary non-executable file additions/modifications beneath explicit approved roots. It rejects traversal, ambiguous/duplicate paths, hidden files, symlinks, executable modes, deletions, dependency manifests and sensitive paths. `authorize_publication` requires an unchanged exact PR head and successful required checks tied to the proposed patch tree, including the complete trusted required-check set. Five tests cover these boundaries; 30 local tests pass overall.

These validation functions are not a sandbox. Their manifest and check evidence must be derived by a trusted supervisor from actual Git objects and independently executed checks, never accepted from agent-produced JSON. The gated publisher below derives the manifest/content and uses an atomic expected-head mutation; live App writes and full isolated-worker integration remain unverified. A valid manifest does not prove safe source-code behaviour.

## Actual Git patch inspection

`inspect_patch` accepts at most 256 KiB, verifies an exact local HEAD and applies the patch only to a temporary Git index. It derives paths, operations and modes from the resulting Git tree before calling the manifest validator; worker-provided manifests are not used. Git subprocesses use argument arrays, a restricted environment, disabled hooks/fsmonitor/replacement objects and a fifteen-second per-command timeout. No working files or normal index are changed; unreferenced objects may be written to the disposable clone. Four real-Git tests verify resulting content, worktree/index preservation, malformed patches, moved heads, sensitive files and deletion rejection. All 34 local tests pass.

Use only a supervisor-created ephemeral clone. This inspection is not an OS sandbox and must not be run against an arbitrary pre-existing repository controlled by a worker. The trusted supervisor still needs to materialize/check the exact tree inside the isolated runner, verify a complete check set and enforce output/runtime/spend limits. Patch inspection now rejects mode changes on modified files as well as unsupported file types, and disables lazy object fetching/all Git network protocols.

## Owner enablement ledger

`Enablement` starts disabled, stores owner approval references for App/endpoint/agent/budget plus five distinct dry runs, and requires a separate explicit owner switch. Duplicate approvals do not count twice. Revocation disables automation and removes approvals, requiring a fresh audit. Five tests cover missing approvals, duplicate dry runs, wrong-owner actions, explicit switching, persistence and revocation. Local suite: 39 pass, two Docker probes skipped locally.

This ledger is not an authentication mechanism: the future administrative adapter must authenticate the owner independently and must never take authenticated_owner from webhook, repository, agent or ordinary request-body input. Approval references must bind reviewed immutable configuration and successful dry-run artifacts. The worker must compare the current App/endpoint/agent/budget configuration to those exact references before starting; configuration changes require revocation and renewed approval. No administrative endpoint or enabled coding worker exists yet. The ledger alone does not establish that five real owner-approved dry runs occurred.

Enablement now requires exact immutable references for all four setup components on every readiness check. Each dry-run approval is bound to the canonical SHA-256 configuration fingerprint, and the explicit enable switch is bound to that same fingerprint. Changing any reference requires five dry runs for the changed configuration and a fresh switch, even if the previous configuration was enabled. Legacy approval rows cannot satisfy the new fingerprint gate. Local suite: 41 pass, two Docker probes skipped.

## Webhook HTTP adapter

`Webhook` provides a WSGI POST endpoint at /webhooks/github, accepting JSON with an explicit length of at most 1 MiB. It preserves raw bytes for signature validation, rejects truncated/malformed input and returns generic errors without request details. Unexpected failures return 503; invalid deliveries return 400. It does not expose administrative enablement methods. Five HTTP tests include real signed intake/durable deduplication and tamper rejection; 46 tests pass locally with two container tests skipped.

Deploy only behind a reviewed HTTPS server/proxy that enforces body/header limits and read timeouts before WSGI buffering. The adapter cannot impose a socket read timeout itself. A single intake/database instance must not be shared unsafely across server threads: create per-request connections/factories and use bounded workers. Configure redelivery/reconciliation explicitly; an error response alone does not guarantee GitHub will retry. Endpoint hosting, installation credentials, production server and operational recovery remain unconfigured.

## Gated same-branch publisher

Publisher requires configuration-bound enablement before preparing a write and again immediately before mutation. It refetches the authenticated review/PR, requires the approved bot and repository, an open same-repository unprotected/non-default PR branch, unchanged reviewed head and current actionable finding. It derives the actual patch tree/manifest with inspect_patch and checks trusted required-check evidence against that tree. It reads immutable ordinary-file blobs with all Git protocols/lazy fetch disabled, caps total publication content at256KiB and sends only those base64 file contents, a fixed commit headline and expectedHeadOid to GitHub createCommitOnBranch. No review body enters the mutation. Modified file modes must stay100644, matching the mutation's supported file semantics.

GitHub atomically appends the commit and moves the same branch only if expectedHeadOid still matches. This avoids a separate non-atomic read/update-ref sequence. The adapter checks the returned commit/tree IDs and never retries a mutation internally. A timeout, malformed response or mismatched tree is an unknown publication outcome requiring human reconciliation; do not release a cost reservation, retry with a new head, approve or merge automatically. The API mutation authors the commit as the credential owner, so the injected API transport must use the approved App installation identity in the trusted publisher boundary, never a coding-worker or desktop credential. Branch protection/owner revocation and review state must still be supervised across the small external-call race window.

Five tests use real Git objects, a fake API and synthetic local enablement fixtures to verify the disabled switch, exact contents/head/branch payload, missing checks/stale finding refusal, a server-side head race without retry, finding edits during preparation and revocation during the final metadata fetch. The complete review snapshot must remain unchanged, and enablement is checked after the final fetch immediately before mutation. These fixtures are not real owner-approved dry runs or live API evidence. Local suite:52 tests pass, two Docker probes skipped locally (54 total). No remote write was attempted. Full supervisor/budget/attempt/deadline integration, App permission acceptance, live same-branch CI rerun and sanitized explanation remain incomplete. ## Durable execution handoff

`Supervisor` connects the existing enablement, intake and budget stores on one durable SQLite connection. `prepare(job)` checks the approved configuration, revalidates the current finding, obtains the shared per-PR attempt lease, assigns a unique run identity and reserves the operator-supplied known worst-case micro-USD cost before returning a reference-only execution request. The UTC month comes from a trusted clock, never the webhook; the deadline is the earlier of300seconds or the next UTC month boundary. A missing/exhausted month budget consumes the attempted handoff and flags needs-human without returning work. Configuration stays disabled by default; local test approvals are fixtures, not owner acceptance.

Attempts now persist an explicit dry_run/execution mode. Existing databases migrate prior attempts to dry_run, and finish_dry_run cannot close an execution lease. Both modes share the same three-attempt ceiling and one-running-attempt lock across comments and heads. Interrupted handoffs retain the running lock and any cost reservation. There is no automatic restart, retry, reservation release or expired-lease takeover. Reconciliation must first prove that the original worker/container has stopped.

`can_continue(run)` is a fresh enablement/deadline/reservation check for the trusted controller, not permission for a worker to publish. `finish` must be called only by that controller after it has verified all processes and model calls have stopped and the check/publication phase has reached a known outcome. Its successful status means the execution lifecycle completed; it does not independently prove patch correctness, CI results or remote publication. Supply actual cost only from trusted gateway/provider reconciliation, never agent output. Unknown cost retains the full reservation and flags needs-human; known overruns are recorded and block spending above the configured ceiling. Failure, expiry and revocation also require human review.

The handoff deliberately starts no process and exposes no webhook/admin route. It does not enforce an OS timeout, restrict model requests, calculate prices or authenticate an administrator. A production controller still needs the reviewed isolated coding worker, hard process termination/model-token ceilings, trusted price/billing source, independently executed checks, gated publisher integration, and remote CI rerun/explanation. Do not enable paid work based on these component tests. Ten new integration cases use real durable stores and synthetic metadata/owner approvals to verify disabled operation, handoff reservation, budget rejection, month cutoff, restart locks, unknown cost, overrun, revocation, cross-head attempts and legacy-mode migration. Local suite:62 pass, two Docker probes skipped (64total). No agent, paid request or remote mutation was executed.
